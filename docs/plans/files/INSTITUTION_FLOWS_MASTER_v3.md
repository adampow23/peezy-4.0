# §A. The Template — a thin state engine plus optional modules

## A1. Principles
1. **No unowned state:** every unresolved obligation has an owner, a next action, a trigger (date or event), and an exact resume destination. Exits users can tap are not enough; the obligation itself must be accounted for.
2. **Perfect amount of detail, nothing more** — max one mandatory question before useful guidance (institution identity excepted when genuinely required); a normal row reaches an accounted-for disposition in ≤4 decisions.
3. **Never punish self-reliance** — there is no downgraded self branch because there is no help/self fork (A3).
4. **More complex situation → more help, never less.**
5. **Evidence honesty** — exact policies, fees, deadlines, and delivery requirements are source-backed or explicitly labeled unverified. Never present model reasoning as confirmed fact. This includes time and ease claims ("takes minutes," "same day," "usually no deposit"): verified, labeled as estimates, or cut.
5b. **High-consequence exceptions surface before the completion CTA**, never only as post-contact chips — conditionally, from profile data, research, or a user-invoked hatch, so unaffected households never see them.
5c. **Internal grain stays subject-specific; the interface consolidates repeated work.** Obligations key per person/pet/vehicle/property/service (A7); the visible surface groups them into one card at 2+ identical items, each item keeping independent state.
5d. **The interface says what the institution said, not what Peezy computed.** A Peezy planning target renders as pacing, never as a deadline word; a locator match is not an assignment; a mailed confirmation is not observed effect; a lender's "sent" is not receipt.
6. **Catch frustration at the moment it happens** (inline closeout + support on every row).

## A2. Disposition model and completion
A row is **finished** only when `COMPLETED` or `NOT_APPLICABLE`. It is **sorted for now** when its disposition contract is filled.
- `COMPLETED` — real-world obligation fully handled.
- `NOT_APPLICABLE` — the row was generated incorrectly or the household holds no obligation on it (see the reason resolver in A8).
- `USER_ACTION_TRACKED` — a specific person has a specific action and due date.
- `WAITING_ON_EXTERNAL` — institution/other person is acting; a verification trigger exists.
- `DEFERRED` — nothing appropriate yet; a date **or event** will reactivate it.
- `SUPPORT_ACTIVE` — a person is helping; visible status + expectation + self-service fallback intact.
Every non-complete disposition stores: `owner · next_action · next_trigger · resume_destination · visible_status_copy`.

**The case is the row.** Every entry declares its case objects (per child, service, property, vehicle, person, filing). Each case carries a `REQUIRED_MILESTONE_PROFILE` derived from its role or disposition; milestones outside the profile are `NOT_REQUIRED(reason, source)`, never silently completed. **A case is `COMPLETED` only when every profile-required milestone is `COMPLETED` or `NOT_REQUIRED`.** Money, mail, title, and receipt tails that are in the profile keep the case sorted-for-now. **Independently keyed non-blocking companions** (Entry 9's voter companion) keep their own disposition and never block the parent case unless the entry puts them in its profile.

**WAITING_ON_EXTERNAL contract:** every waiting state shows, without a submenu — who owns the next step · what they're expected to do · when they said they'd do it (or a risk-based follow-up date derived from the protected outcome's timeline, never a generic fixed interval) · what happens if they don't · what backup protects the outcome · where the user resumes. Always two one-tap exits: "It happened" (→ outcome question) and "It's stuck" (→ support with the named office). Second failed cycle changes channel and surfaces a pre-scripted nudge template — never a third identical "still waiting?".
**Trigger hierarchy, mandatory everywhere:** institution-promised date → recipient's required acceptance date → safe threshold derived from remaining recovery actions → user-adjustable check date bounded by that threshold → **when the latest safe date has passed: immediate urgent-recovery card, never a backdated reminder.** Generic family-wide constants chosen without reference to the outcome are not permitted in entry text; **risk-based checkpoints an entry derives from its protected outcome remain valid and locked** (Entry 2's adjustable records check, Entry 4's IEP pre-start / day 1–3 / promised-date verification, Entry 5's first-fill close); a labeled adjustable estimate may exist only as the final fallback when no safer threshold is derivable. Two triggers are normal: a short check trigger (recipient's stated turnaround) and a hard trigger (the governing date minus recovery buffer).

**Silence is not failure — and silence is not completion.** Observed-delivery milestones ("first forwarded item") are never mandatory unless the obligation itself requires confirmed receipt (records at the new school or office, plates at the old state, a fill the person needs). Where receipt is required, silence means the WAITING trigger fires and the second cycle changes channel — never a quiet close. Issue rescue for the non-mandatory kind is trigger-only.

Completion copy is truthful: "**You're set for now** — 2 completed · 1 waiting on the office · 1 coming back after your move," never a false "All done." Reminders, chips, "stuck," and support are **transition mechanisms**, not competing statuses. Cross-entry guards are stated as named events and invariants (A11), not prose.

## A3. Visible flow shape (screens, not steps)
> compact roster → one consequential decision → institution identification *only if needed* → immediate best-action card → contextual outcome question → tracked disposition → next row

- **No help/self decision screen.** Peezy leads with the easiest useful route; "Already handled" is always one tap; "I'll use my own method" is a quiet secondary that gets the same deadlines, scripts, and warnings, tracked as `USER_ACTION_TRACKED` (never an exit).
- Title is a header, not a screen. Research happens inside the card. Closeout is inline. Spawns don't interrupt (A7). Support is an action on the row, not a new flow.
- **One-row focus:** "Next: Bright Smile Dentistry — 2 of 4 sorted for now." Full roster compact underneath; finished rows collapse to a Done section; the single next best action is visually dominant.

## A4. External-handoff contract
Before any call / portal / website / form / mail / map CTA:
1. Persist the exact row + expected action; mark **in progress, never complete**.
2. Define the action-appropriate return question.
3. On return — immediate or next-day — resume **at that row** with context: "You were contacting Little Sprouts about written notice. What happened?" A returning user after time away also gets a one-line "since you were gone" recap when anything changed.
4. Result card, number, script, deadline, and prior answers all survive the round-trip.
5. **Time-aware primary CTA:** at 9pm with the office known-closed, lead with "Call tomorrow at 9:00 AM" (schedules the reminder); the number stays available beneath.

**Contextual outcome questions** (shared states, contextual copy — chips appear only after intent; primary outcomes ≤5; every outcome lands in an owned state):
- After a call — "What happened?" → *Fully handled / They're handling it / I need to do one more thing / I couldn't finish*
- After a portal — "Did it work?" → *Got what I needed / They're processing it / I need to submit something else / It didn't work*
- After written notice — "Where did you get to?" → *Sent / Ready to send later / I need proof or another document / Couldn't complete it*
- "I couldn't finish" reveals: *Try another route / Do this later / Get help from a person.* Entry-specific chips render only under "I need to do one more thing," with free text always visible.

**Legal trigger ≠ move date** (scoped to **published institutional windows** — DMV, school enrollment, some utilities; entry-declared consequential anchors in A9 — last day of care, refill-before-departure, service start the day before move-in, billing-stop — remain valid clocks). Every published-window deadline stores `LEGAL_TRIGGER` (the event the official rule names) · `TRIGGER_DATE` (derived from the best evidence the rule permits — wallet document, institution response, system-observed event, or explicit user-confirmed event — with confidence stored separately; else `UNRESOLVED`) · `PUBLISHED_WINDOW` (with source) · `LEGAL_DEADLINE` (shown only at high confidence) · `PEEZY_TARGET` (pacing copy only) · `DEADLINE_CONFIDENCE`. Peezy never substitutes the move date for a legal trigger and never invents a "safe date." **Unresolved window or trigger → one visible card, two owned obligations:** the card's primary action is `USER_ACTION_TRACKED` (user: begin the official route now); the verification is a quiet substate on the same card ("Confirming the official deadline") with its owner (research or a named verifier) and trigger (before the user's next irreversible step) stored on the row. It becomes a visible `WAITING_ON_EXTERNAL` line only when the verification result can change the next irreversible action, and `SUPPORT_ACTIVE` only when a person has accepted the work under a backed SLA or the user taps stuck. Whichever resolves first enriches the transaction.

**Delivery-address checkpoint** (scoped to **inbound artifacts an institution sends to the household** — cards, plates, titles, refund checks, records sent to self, and other mailed documents with a user-confirmable delivery address). USPS COA validation/notification letters follow the addresses already confirmed on the filing — Entry 10 note only, never a second checkpoint. Records follow the sender's delivery and replacement route; sensitive records never default to forwarding as recovery. Outbound mail the user sends (written notice, certified mail) keeps its pre-populated send-by task and is not gated. Any transaction that mails an inbound artifact confirms the destination address before it closes (`DELIVERY_ADDRESS_CONFIRMED`) and carries misdirected-mail recovery. Recovery is artifact-specific: government credentials and titles are treated as non-forwardable (agency correction or replacement only, verified per agency); checks follow the institution's stated handling. No fixed mailing interval: agency-stated time → issue date + processing guidance → labeled user-adjustable estimate → before a dependent event.

**Dependency-conflict route.** When two institutions each wait on the other (carrier vs registration authority; lender vs carrier; records vs enrollment; management vs provider), one card names both, asks each what it accepts provisionally, escalates, and opens support with both named. Explicit exits: provisional proof accepted · one side offered a first route · still conflicting → escalation / alternative · support active. The support door is on the card from the first render, beside the scripts — the user may hand the deadlock to a person without first playing mediator. The user is never sent back and forth without an owner.

## A5. Research and evidence: nonblocking, confidence-tiered
- The first actionable card renders **immediately** from known data; research enriches it in place ("Checking their exact cancellation policy…"). 20s is a backend budget, never a user-facing hostage screen. The card never blocks calling, browsing, or scheduling a return.
- Tiers are **confidence**, not density: **Verified** (exact process/form/deadline located — show as fact) · **Partially verified** (institution + contact route found; safe script + explicit "confirm this when you call" labels) · **Generic** (no confident match; safest general action + manual details + support door as the largest element).
- **Two orthogonal verification postures support the Verified tier.** `RULE_VERIFIED`: an authoritative official source verifies the rule and every applicability predicate Peezy knows (household, person, vehicle, location, transaction) matches. `ACCOUNT_OR_DECISION_VERIFIED`: the carrier, lender, landlord, association, agency, or account document confirms the result for this exact account or submission. An official source can verify a legal window, a published relocation clause, or a document list; it cannot verify that this account is eligible, this office accepted, or this carrier will write the risk. Cards show the posture quietly.
- **Institution capability posture.** An office, channel, or provider is `TRANSACTION_AND_OFFICE_VERIFIED / FOUND_SERVICE_UNCONFIRMED / UNRESOLVED`. A location result, brand match, or territory match is never proof the institution performs this transaction.
- **Every figure renders from data.** Fees, windows, durations, prices, and counts are verified at seed and rendered live; entry text may state seed-date values only as marked examples.
- Manual entry is not punished: attempt research on the typed name/location first; generic only after that fails. Optional website/phone paste, never mandatory.
- Card anatomy: one recommendation, one primary action, one consequential date, one sentence of why — everything else expandable.

## A6. Support: an active state, not an exit
- Copy: **"Want help from a person?"** — never takeover language (delegation stays a hidden slot until fulfillment ops exist).
- Row shows: "Help requested · A person will reply by 9:00 AM · Meanwhile: [self-service route stays visible]."
- SLA is computed AND operationally backed; if missed: internal escalation, visible expectation update, user notified, alternate route intact. One `SUPPORT_ACTIVE` row never blocks the rest of the roster.
- Resolution actions (all land in the task graph): resolve & complete (runs deferred spawn checks) / create-update follow-up / return-to-step with a message.
- **Household handoff is not delegation and ships in v1:** "Someone else is handling this" → tracked owner + shareable handoff message + verification trigger. **Every ledger line, requirement line, and vehicle/person line accepts owner = another household member.** Handoffs share the *task*, never an authorization secret (A7), and never widen visibility (a handoff shares one task, not another adult's accounts).

## A7. Task graph: identity, supersession, wallet, rosters, ledgers
- **Canonical keys include the subject:** `(household, subject_or_patient, institution_or_account, TASK_TYPE)` and, for case objects, `(household, move_event, subject)`. Same pediatrician, two kids = one visual group, two obligations. One person's completion never closes another's.
- **Verbs:** create · enrich · **supersede · retire · reopen**. Every row has **"Change plan"**; switching Cancel→Transfer auto-retires the certified-mail task and its reminders, with brief undo (optimistic UI). Move-date changes recalculate every affected deadline.
- **External amendment.** Supersession that follows a date, address, or scope change retires stale internal tasks **and** creates an immediate external action to amend or withdraw any submission whose evidence went stale (scheduled cancellations, effective dates, accepted proof, appointments, certificates, notices already given). Internal recalculation alone is never sufficient; every milestone with stale evidence reopens. The amendment is a full A4 handoff with its own return question; **the already-sent artifact remains in force and visible until the institution confirms the change**; the new date is not shown as the institution's date until it went through. Re-filing from scratch is never the default. **When a core anchor changes (move date, address), the resulting amendments render as one batched "Update your active dates" card**, each line keeping its own owner and return question, never as scattered alarms. On the institution's confirmation the old artifact flips to *Replaced — [date]* with brief undo and collapses into the row's history; the new date becomes the institution's date only then. Likewise, when several safe dates lapse at once, urgent-recovery cards consolidate into one "Needs attention now" view ordered by consequence.
- **Spawns don't interrupt between rows.** Non-urgent spawns batch into one end summary: "Added to your settle-in plan: choose a new dentist." Urgent independent spawns still fire immediately.
- **Household rosters are owned by §A, seeded by entries, edited per A8:** people (credential kind and expiration when known), vehicles (identity, disposition, lienholder, garaging), properties (role, tenure, responsibility class), institutions. Entries hold references, never copies. **`ROSTER_DISPOSITION_CHANGED` makes every consumer recompute the subject's required milestone profile**: a consumer supersedes only milestones the new disposition makes inapplicable; obligations that survive the disposition (a stored vehicle's lienholder coverage, an old state's active registration) reroute or reopen; each consumer records its reconciliation (A11). A Yes/No assessment flag is never a source of truth; no ghost rows.
- **Household document wallet:** shared documents (lease/closing, utility statement, parent ID, custody orders) resolve once and are referenced by every row/packet that needs them — with independent per-requirement acceptance states, because possession never silently becomes institutional acceptance (`need to get / likely ready / submitted / accepted / rejected — replacement needed / not required / waived`). **Shared documents are qualified per requirement** (name match, address match, age, type, alternate route). Sensitive documents are trackable ("I have this") without upload; upload is optional with visible storage/transmit/delete controls; identity documents are track-only.
- **Sensitive credentials and codes use three handling classes.** *Identity-prohibited* (licenses, card numbers, one-time codes): never captured, entered, or stored. *Modify-keys* (a code that can act: modify, cancel, redirect): stored as existence and retrieval location only ("USPS confirmation email received, Aug 26"); handoffs share the task, never the key. *Evidence-only* confirmation numbers (a utility order number) may be stored as values.
- **`ADDRESS_UPDATE_LEDGER`** — household container keyed `(household, move_event)`; **lines keyed `(household, move_event, subject, sender_or_account, address_role, address_leg, owning_case, owning_milestone)`** where `address_role` ∈ mailing / billing / residential / service / garaging / delivery / legal / registry and `address_leg` is the old→new transition. **The ledger watches; it never owns.** A line is a read-only projection of its owning milestone's disposition **and** transition state: `A4 handoff in progress→IN_PROGRESS · USER_ACTION_TRACKED→NEEDS_UPDATE · SUPPORT_ACTIVE→ASSISTED · WAITING_ON_EXTERNAL→WAITING_ON_SENDER · DEFERRED→BLOCKED_WITH_TRIGGER · COMPLETED→UPDATED · NOT_REQUIRED or NOT_APPLICABLE→NOT_NEEDED`; it never writes back, never completes an account, and an owning case never completes because a line changed. **An entry emits a ledger reference only when it owns a real address-update obligation for that subject, account, address role, and leg** — presence in an institution roster creates no line. Unmapped adds from forwarded mail are lightweight `USER_ACTION_TRACKED` lines owned by Entry 10 only until matched; **creating an owning milestone consumes every unmatched discovery with the same (subject, sender, address_role, address_leg) before E13 fires**, so one line exists per obligation. An unmapped item that belongs to another adult carries a one-tap **"Pass to [household member]"** that re-subjects the discovery across the visibility wall. Populated by references, one-tap adds, and explicit user adds — never by questionnaire or statement mining. Claims known-sender coverage only. Expiry clocks attach per address leg. Visibility follows the subject (one adult's institutions are not another adult's view by default).
- **Conditional modules render from profile or rescue triggers only** — protected-situation content never adds questions or copy for households it doesn't apply to, and generic copy never overrides a protected household's actual rights.

## A8. Roster component
- Rows from assessment counts and §A rosters; **the roster is editable** — add, remove, rename, merge, reassign person. A wrong assessment count is fixed, never "skipped" to fake 4-of-4.
- **"Skip" does not exist.** The row menu is the disposition menu: *Already handled / This doesn't apply / Come back later (date-or-event) / Someone else is handling it / I'm handling this outside Peezy / Edit this list.*
- **"This doesn't apply" is honored as the user's assertion, never silently reinterpreted.** When no stored evidence contradicts it, one tap → `NOT_APPLICABLE(reason = user_asserted_no_obligation)` and the row is gone. **Only when stored evidence says the obligation persists** does a minimal reason resolver appear — *wrong person or item · the fact changed · we no longer use them · handled by another source · other* — with the basis stated and the options *edit the underlying fact · someone else is handling it · handle it outside Peezy · back to the task*.
- Fast-exits are first-class on every row from the first screen. Nothing re-asks a resolved row. Category-level "I'll come back to all of these" defers the group with one trigger.

# Entry 4 — SCHOOL · v2 LOCKED (post round-3 adjudication)

**The structural verdict of the round:** school is not an institution-contact problem — it's a **placement-and-start-readiness problem**. The parent's outcome: *each child has a confirmed path to a school, can start on the right date, and loses no services or time because something was missed.* Entry rebuilt around four objects: one transition case per child · an active placement plus a prepared fallback · independently tracked readiness milestones · a waiting contract on every external decision.

## 4.1 Canonical object and routing (distance heuristic removed)
**`SCHOOL_TRANSITION` — key `(household, child, move_event)`.** COA_SCHOOLS and SCHOOL_TRANSFER become generation reasons/aliases, never separate obligations (no duplicate school tasks when an address corrects or routing reclassifies).

**A transition classifier replaces mileage** — a 5-mile move can cross district lines; a 500-mile move can preserve a charter or virtual relationship. Derived from: current school + type, both addresses, both districts, destination grade, effective academic year, move timing, known program/transfer status. Classes → routes: same relationship valid → update route · new assigned school, same district → assigned-vs-stay route · new district → enrollment route · charter/magnet/choice → eligibility-continuity route · private → admission route with public fallback · first enrollment → enrollment only, no withdrawal side · **address not confirmed → prepare-documents-now route, placement DEFERRED on address confirmation** · homeschool/no-enrollment → exit cleanly ("this child won't enroll for this move"). The classifier asks a question only when a fact is materially ambiguous ("Is Lincoln your assigned public school, a charter/magnet, or private?" changes everything; mileage changes nothing).

## 4.2 One visible case per child, milestones underneath
Case body: **Placement · Enrollment · Current-school closeout · Records · Start readiness · Conditional services.** Milestones are independently stateful; the parent sees one journey per child. Each child's case declares its `REQUIRED_MILESTONE_PROFILE` by route (same relationship → address update only; new district → placement, enrollment, closeout, records, start readiness; conditional modules add milestones only when triggered); non-applicable milestones are `NOT_REQUIRED(reason, source)`; a case COMPLETES only when every required milestone is complete or not required (§A A2). Backup school = an object inside the case, never a duplicate task. "Change plan" swaps the active destination and retires stale milestones (§A7 supersession). Family summary is the first screen: the app has already done the research — "Maya — new district · Lincoln shown by the official locator · **Next: start enrollment**. Noah — same school · **Next: update household address**. Ava — private admission pending · public fallback ready · **Nothing needed today**."

## 4.3 Routing evidence ≠ placement status (both tracked, both honest)
**Evidence:** `REGISTRAR_CONFIRMED / OFFICIAL_LOCATOR_MATCH / NEEDS_CONFIRMATION / UNRESOLVED` — every lookup stores source, date, academic year, destination grade, address used. Locator results also carry the §A A5 office posture `TRANSACTION_AND_OFFICE_VERIFIED / FOUND_SERVICE_UNCONFIRMED / UNRESOLVED` for the enrollment office. **Peezy runs the official district locator itself whenever technically possible** — with the destination grade and the effective school year (summer moves check next year's boundaries; grade bands differ). The parent repeats a lookup only when Peezy can't complete it or a defined ambiguity exists (address unrecognized, multiple results, boundary change, capacity caveat, program override) — then the card deep-links the official tool with the address ready. **Status:** `CANDIDATE_IDENTIFIED → REQUEST_OR_APPLICATION_PENDING → ASSIGNED_OR_ADMITTED → ENROLLMENT_SUBMITTED → ENROLLMENT_ACCEPTED → START_DATE_CONFIRMED`. Copy pattern: "Lincoln Elementary is the school shown by the district's 2026–27 locator for Maya's 6th-grade address. This identifies the expected school; enrollment isn't confirmed yet." Never "Maya's school is Lincoln" from a dataset; never "call and check" when Peezy already checked. Quiet escape on every placement card: **"That's not our school"** → declare charter/magnet/choice/private → reroute; the zoned result becomes the fallback, never overwrites the intended plan.

## 4.4 Transition timeline (replaces any single date anchor)
Tracked dates, derived where possible, asked only when one changes the action: current school's year-end · child's planned final attendance date (≠ year-end) · transfer/application deadline · expected decision date · **safe fallback date** · new school's opening date · child's confirmed first attendance date (≠ school's first day) · document deadlines · service-confirmation checkpoints. Three timing modes: **midyear** (secure destination → set final attendance date → coordinate both ends → account for any gap) · **between years** (no manufactured withdrawal unless the school actually requires one; closeout = property return + records assurance) · **first enrollment** (no withdrawal side). Processing expectations are verified-or-honest: the district's published window as fact, else "no published time — we'll track their response and check before [child]'s safe start date." Move-date or address changes recalculate the whole timeline **and**, for any submission whose evidence the change made stale (an enrollment or stay request carrying the changed start date or address; a records request only if the receiving school changed), create `USER_ACTION_TRACKED` "update your submission with [district/school]" as a full A4 handoff; the submitted request remains live and visible until the district confirms; stale milestones (safe fallback date, decision date) reopen (§A A7).

## 4.5 Local routes
**Same relationship:** lead with the one required action ("Update the household address through the district portal") — residency proof, transport, emergency contacts, pickup auths surface **conditionally**, only when the district requires them or the fact changed. One submission covers all children when the district allows. The address update emits `ADDRESS_UPDATE_REFERENCED` (E13) per (child, district/school, residential, leg), consolidated visually only under a verified single household submission; each child's acceptance state stays independent. Outcome: *Accepted / Submitted — waiting / They need another document / Couldn't submit.* Status stays honest: "Address accepted · Bus assignment pending."
**Assigned school changed:** the decision card states the verified facts **before** the choices — new assigned school; the district's actual continuation policy (**verified conditions, or the exact registrar question when unverifiable — "can usually finish the year" never ships as a promise**); transport consequence on the same card (verified, "couldn't verify — confirm before submitting," and never universal copy: protected students can have school-of-origin transport rights). Choices: *Switch / Request to stay / Decide later (DEFERRED, bounded by transfer deadline or safe fallback date).* **Every stay request carries: expected decision date · safe fallback date · backup school · backup packet readiness.** If undecided at the safe fallback date: "Roosevelt hasn't decided. To protect Maya's first day, finish Lincoln's packet now — this doesn't withdraw the request" (parallel enrollment only where the district permits; otherwise prepare without misrepresenting).

## 4.6 New-district route — destination-first
Order: establish destination → start enrollment (online pre-enrollment surfaced when it exists; honest when it doesn't: in-person window + what to bring) → records route → current-school closeout → start readiness. **Never instruct withdrawal before the destination path is accounted for.**
**Records: the receiving school owns the default** (FERPA permits school-to-school disclosure on enrollment) — "Start enrollment with Lincoln; they'll request official records from Roosevelt." Give the new school the old school's name, district, registrar contact, student identifiers. Parent work is created only when a signed release is required, the receiving school asks, records stall, or something time-sensitive precedes the transfer. Parent keeps a **minimal backup packet** (latest report card/transcript, current schedule for secondary, current IEP/504, health/medication plan, shots record if handy) — not a reproduction of the official transfer. Verification is risk-based: school's promised date · before first day when records affect placement · before scheduling when transcripts affect credits; "records pending" is never confused with "enrollment denied," and the row closes on **confirmed receipt**, not on "they said they'd send it."
**Closeout is institution-specific:** research what the old school actually requires (withdrawal form, last-attendance notice, device/book/instrument return, release) — no universal withdrawal step.

## 4.7 The enrollment packet — a blocker map on the household wallet
Requirements are the **destination's verified list**, or honestly labeled: "commonly requested — Lincoln's exact list still needs confirmation." (No universal checklist; even "lease or utility, not a license" varies by district and is retired as universal copy.) Each requirement carries a consequence class — `NEEDED_TO_SUBMIT / NEEDED_BEFORE_START / CAN_FOLLOW_AFTER_START / ONLY_IF_APPLICABLE` — so a missing transcript never masquerades as urgent as missing residency proof. Wallet + per-child packet views per §A7: shared docs resolve once, acceptance tracked per requirement, possession ≠ acceptance, no required sensitive uploads, packet lines promote to standalone tasks only on separate owner/deadline/external dependency.
**Residency rescue:** show every district-approved option the household already has; link SETUP_UTILITIES only when a utility statement is genuinely the easiest accepted route. **"I don't have any of these"** always reveals alternatives — shared-residence affidavit, pending lease/closing, registrar verification, and the housing-instability module below. **Immunization/physical:** lowest-work source hierarchy (household record → state immunization registry → prior school → current pediatrician → health department); a missing item spawns `COMPLETE_SCHOOL_HEALTH_REQUIREMENT`, and `CHOOSE_NEW_PROVIDER` only when an ongoing relationship is actually needed. Provisional-enrollment rules surface when research finds them ("she can start while shots catch up") so a missing document never feels like a locked door. Emits `DESTINATION_ID_REQUESTED` (E11) with reason `ADDITIONAL_REQUIREMENT` when the district requires a destination-state ID and `OLD_ID_REJECTED` when it rejects the out-of-state one; emits `SCHOOL_HEALTH_REQUIREMENT_OPENED` (E15a) per missing immunization/physical item and consumes `HEALTH_EVIDENCE_AVAILABLE` (E15b), district acceptance separate (I2).

## 4.8 Conditional services (IEP and 504 are separate modules; copy is conditional, never universal)
- **IEP, public→public, same school year:** "The new district must arrange services comparable to Maya's current IEP, in consultation with you, until it adopts or replaces it." (In-state vs out-of-state noted; re-evaluation possible out-of-state; the old plan holds as comparable services meanwhile — *comparable, not identical*.)
- **504:** different rule, different copy: "Send the current 504 before her first day and ask the district to confirm in writing what accommodations apply while it reviews."
- **Private destination:** never inherits the public comparable-services promise.
- **Verification replaces the fixed +10 days:** pre-start (named case manager/504 contact · initial services · transport/health/behavior support · next review date — via a one-tap copy-paste email template with the child's details filled) → day 1–3 ("did services actually begin?") → the district's promised adoption/review date. Silence or "services haven't started" → written follow-up template + named special-ed/504 contact + support door. Support supplements the parent's direct route, never replaces it.
- **School health plan module** (asthma/diabetes/seizure/allergy, from profile or packet): nurse contact, medication authorization, action plan, delivery rules — **start-readiness blocks on it**; enrollment complete ≠ start-ready while the nurse hasn't accepted the plan.

## 4.9 Protected-transition modules (trigger-only, rescue-first)
Housing instability ("staying with relatives / hotel / no proof of residence") → immediate-enrollment right + district liaison route instead of a lease dead-end; school-of-origin and transport rights can flip the stay-vs-switch card. Foster placement → stability/immediate-enrollment/transport protections; the ordinary address card is insufficient. Military-connected → Interstate Compact module (records, placement, eligibility, special ed, graduation). Shared custody → the smallest question only when the profile shows two households: "Which residence does the district use for enrollment?" — then the district-specific rule.

## 4.10 High-school credits (order corrected)

A junior/senior case isn't start-ready while the graduation path is materially unresolved. Grades 9–12 get one athletics line in the same counselor touch ("eligibility rules differ — ask the athletic director"); no eligibility engine.

## 4.11 Private / choice — bounded v1 branch (not deferred, not a marketplace)

Charter/magnet: the address result is the fallback; the choice relationship is the plan. No discovery, ranking, financial aid, or interview tracking in v1.

# Entry 5 — PHARMACY · LOCKED (round 4; rebuilt per review)

**Modules:** pull path · capability-postured chain shortcut · supply-protection deadline logic · conditional controlled-medication continuity · urgent-continuity hatch · WAITING on fills, not promises.
**Roster:** rows per person × pharmacy (§A5c: one household card groups them). Mail-order rows are their own type. Nudge remains entry.

## 5.1 Chain shortcut — a capability, not a brand match
Brand equality never implies a shared dispensing system (franchise banners, acquired brands, and specialty/mail/compounding channels under one parent all break it). Postures: `SHARED_RETAIL_SYSTEM_VERIFIED` (official chain guidance or authenticated account action confirms the shared profile → shortcut) · `BRAND_MATCH_ONLY` / `UNKNOWN` (→ standard pull path) · `SEPARATE_CHANNEL` (→ channel-specific route). Shortcut card: "Your profile can be used at [location] — make it your preferred store" (never "records are national"), with a quiet standing escape: "Specialty, compounding, or clinic pharmacy? Tell us — that's a different move." **Two milestones per row:** `DESTINATION_PHARMACY_SET` and `MEDICATION_SUPPLY_ACCOUNTED_FOR` — a store change completes the first only. These are the case's `REQUIRED_MILESTONE_PROFILE` (mail-order rows add the shipment-redirect milestone); the case COMPLETES only when all are complete or `NOT_REQUIRED`. `SHARED_RETAIL_SYSTEM_VERIFIED` is this entry's §A A5 capability posture (`TRANSACTION_AND_OFFICE_VERIFIED` for the destination store); a brand match without system verification renders `FOUND_SERVICE_UNCONFIRMED`. The row closes on **first fill confirmed** or the user's "nothing due before [date]" (→ DEFERRED to that date); status meanwhile: "Store changed · one prescription still needs a plan" when an exception is open.

## 5.2 Transfer path
"Pick your new pharmacy" — the verified same-system store is **recommended with its reason**; otherwise neutral nearby results, **never pre-selected** (unanimous). Card: name + DOB + old pharmacy's details, receiving side pulls. Honest timing: "often same visit within a chain; 1–3 business days when records come from another company — estimate." "They're pulling them over" → full WAITING contract (owner = new pharmacy · expectation = pull + fill · trigger = their stated time or next-day check · fallback = fill remaining at old pharmacy if refills exist · resume = this row). The destination pharmacy emits `ADDRESS_UPDATE_REFERENCED` (E13) per (person, pharmacy, mailing, leg) once set. A submitted transfer or home-store change becomes stale only when the destination store or a dated pickup it carries changes → `USER_ACTION_TRACKED` "update the transfer with [pharmacy]" as an A4 handoff, the submitted request staying live until the pharmacy confirms; a move-date change alone with the same store and nothing dated retires only the internal refill reminder (§A A7).

## 5.3 Controlled medications — before the CTA, never only a chip (§A 5b)
Standing line on every transfer and shortcut card: "If any of these are controlled, the new pharmacy may need a pharmacist-to-pharmacist transfer or a fresh script — ask before you leave town." (Accurate, not categorical: a one-time transfer is often permitted; state rules vary.) Triggered by metadata, free text, or the hatch "one of my prescriptions has special transfer rules" → a `CONTROLLED_MEDICATION_CONTINUITY` line with its own contract (owner = destination pharmacy or prescriber · trigger = before supply-end or last practical prescriber day). The prescriber follow-up is **its own task keyed to person + prescriber** — cross-linked to, never owned by, Medical Records (record transfer ≠ prescription issuance). Emits `PRESCRIBER_ACTION_REQUIRED` (E16a) per (person, prescriber, medication); the continuity line closes on `SCRIPT_OR_ALTERNATE_CONTINUITY_CONFIRMED` (E16b).

## 5.4 PROTECT_MEDICATION_SUPPLY (replaces "refill everything −7")
Keys per person; one household card ("Adam — one may run out near arrival · Emma — no known issue"). Trigger hierarchy: known supply-end/refill-eligible date → insurance change date → travel departure → prescriber availability → **fallback: planning check ~2 weeks pre-move, labeled as a Peezy buffer, not a pharmacy rule.** Lead action: "open your pharmacy app and check anything due before [protected-through date]" — never "count pills," never a refill task for meds that aren't due. Mail-order rows anchor to days-of-supply (or "order by move−14") and carry a quiet "a shipment is already scheduled or in transit" escape → tracked redirect/hold with address-accepted verification. One-tap household dismiss for people who know they're fine.

## 5.5 URGENT_MEDICATION_CONTINUITY (the "I'm low" hatch, end-to-end)
Hatch opens a dedicated per-person card that leads with the safest action, no interrogation: **"Call [current pharmacy] first — fill what's fillable today, transfer the rest after."** (Never empty the last fill into a transfer queue.) Post-call ownership: fillable today → WAITING to promised ready time → pickup tracked before supply-end · new script required → prescriber owns it, shareable message with the new pharmacy's e-prescribing details · insurance/too-soon/prior-auth → insurer or prescriber owns it, reference number tracked · out of stock → pharmacist names the next route (other location / prescriber) · nobody reachable → after-hours prescriber route + pharmacist line + support; Peezy never advises whether skipping a dose is safe. After-hours: time-aware CTA + nearest 24-hour option (labeled). Every state resumes at this card; never COMPLETED from the hatch tap.

## 5.6 Outcome (action-specific)
After a store change: *Changed / App wouldn't do it / One or more prescriptions missing / I need a pharmacist.* After a transfer request: *Ready for pickup–delivery / They're requesting the eligible ones / One or more need another step (chips: new script · controlled transfer check · insurance–prior auth · out of stock or delayed · not in network · other) / They can't find or accept it / I couldn't finish.* Ready-not-obtained → USER_ACTION_TRACKED due before runout. Some-moved-some-didn't → only the unresolved medication lines stay open. No first-fill wait for a 90-day med nobody needs soon — "nothing due before [date]" closes honestly.

## 8.0 Scope boundary (unchanged)
Peezy tracks **timing, proof, gaps, external ownership, and money**. It never recommends coverage amounts, deductibles, endorsements, or carriers, never ranks quotes, and never infers coverage from document labels. Reframed-as-question lines survive only where the question changes an action. `quoteTracker` is cut; "Quote received — deciding" is a disposition with an optional one-line note.

## 8.1 Canonical objects and completion
**Invariant: every interval during which the household owns, leases, occupies, stores belongings at, or garages a vehicle at a property is covered, explicitly declined where no external requirement exists, or waiting on a named licensed professional's determination.** A deliberate gap between residence policies is legitimate if accounted for; two simultaneous properties are not an overlap defect.

- **`PROPERTY_INSURANCE_CASE` — `(household, move_event, property)`**, role `LEAVING / ARRIVING / RETAINED / TEMPORARY`. The nine setup/transfer/cancel × type rows and GET_HOA_MASTER_POLICY are aliases. Household card consolidates at 2+, pairing old and new.
- **`AUTO_POLICY_TRANSITION` — `(household, move_event, policy)`**. Vehicle identity lives **only on the shared household vehicle roster** (Entry 9 §9.4; seeded by this entry, owned by neither); policy cases hold references. Each referenced vehicle carries a **policy-membership interval**: `source_policy · resulting_policy_or_account · covered_from · covered_until · coverage_disposition (STAYS_ON_SOURCE / MOVES_TO_SUCCESSOR / SPLIT_TO_DIFFERENT_ACCOUNT / REMOVED_AFTER_SALE / REMOVED_TO_OTHER_OWNER) · account_owner`. A source policy can stay active while individual vehicles leave it; one vehicle's rewrite closes only its line. Household card at 2+ policies.
- **The case is the §A2 row.** Each case carries a `REQUIRED_MILESTONE_PROFILE` derived from role/disposition; non-required milestones are `NOT_REQUIRED(reason, source)`, never silently completed. **Case `COMPLETED` only when every profile-required milestone is `COMPLETED` or `NOT_REQUIRED`.** Money, mail, title, and follow-up tails keep the case at "sorted for now" (`WAITING_ON_EXTERNAL` / `USER_ACTION_TRACKED`). No second status system.
- Property milestones (profile selects the subset): `COVERAGE_DECISION_ACCOUNTED_FOR · COVERAGE_EFFECTIVE_CONFIRMED · UNDERWRITING_CONDITIONS_ACCOUNTED_FOR · PROOF_REQUIREMENTS[] · OLD_POLICY_DISPOSITION_CONFIRMED · FINANCIAL_RECONCILIATIONS[]`. Profiles: ARRIVING (no old-policy milestone unless a prior policy exists on that property) · LEAVING · RETAINED (use-change route, §8.7) · TEMPORARY / deliberate no-policy (`COVERAGE_DECISION_ACCOUNTED_FOR` satisfiable by the recorded decline; `COVERAGE_EFFECTIVE_CONFIRMED` NOT_REQUIRED).
- Vehicle-line dispositions on the roster (`SOLD_OR_TRANSFERRED / STORED / LEFT_WITH_ANOTHER_HOUSEHOLD_MEMBER / EMPLOYER_OR_FLEET_HANDLED`) **trigger `ROSTER_DISPOSITION_CHANGED` (E1)**: each policy case recomputes the vehicle's required milestone profile, supersedes only milestones the new disposition makes inapplicable, reroutes or reopens survivors (a stored vehicle's lienholder-required coverage stays owned), and emits `ROSTER_CHANGE_RECONCILED` (E2). A source policy cannot keep a live garaging action on a sold VIN.

**Interval guards (enforced):** the LEAVING case of a `FULL_STRUCTURE_OWNER` / association owner completes on `OWNERSHIP_ENDS` + confirmed policy disposition **regardless of the ARRIVING case** — the invariant then attaches to the household's next interval (an ARRIVING, TEMPORARY, or occupying-without-tenure case, §8.2), never to a policy on a property the household no longer owns. For renters, the LEAVING case completes on lease-responsibility end + disposition. New coverage effective later than the responsibility boundary → `USER_ACTION_TRACKED` on the gap (owner = user + agent, trigger = boundary − 1, fallback = support). Old policy running past its boundary with new coverage confirmed → `USER_ACTION_TRACKED` (double-pay). No case COMPLETED while an unaccounted interval exists for the household.

## 8.2 Classifier: tenure first, responsibility second
- Rent → `TENANT_OCCUPANT`. A condo renter never sees master-policy or unit-owner copy.
- Own → responsibility class from documents (wallet) → known property/association data → agent/lender/association confirmation → one question. Classes: `FULL_STRUCTURE_OWNER · ASSOCIATION_SHARED_STRUCTURE · COOP_OR_OTHER_SHARED_OWNERSHIP · SPECIAL_STRUCTURE_OR_UNKNOWN`. Own + House with no association signal → `FULL_STRUCTURE_OWNER`, no question; association known → resolved by documents or a tracked one-line request to management. **Document-triggered reclassify:** when an association or master-policy document later lands in the wallet, or the agent outcome is "they can't insure this as a standalone house," the class and master-document path reopen via §8.5 external amendment.
- **`OCCUPYING_WITHOUT_TENURE`** (family, caregiver, employer housing) — derived from profile or the quiet escape "we're moving in with someone" → an ARRIVING case with the `NONE` recipient class preselected (§8.3 exits). Role stays ARRIVING unless the wallet holds an end date (then TEMPORARY). No renters policy is inferred.
- `newAddressPending` → ARRIVING `DEFERRED`; LEAVING proceeds. `moveDatePending` → labeled estimates, never a cancellation driver.

## 8.3 Three ledgers, one master-document object
**A. Responsibility timeline** — `OWNERSHIP_BEGINS / LEASE_RESPONSIBILITY_BEGINS / OWNERSHIP_ENDS / LEASE_RESPONSIBILITY_ENDS / OCCUPANCY_BEGINS/ENDS / PRINCIPAL_GARAGING_CHANGES`, from wallet documents, shown as approval chips with basis.
**B. Requirement ledger — third-party recipients only:** `LENDER`, `LEASE_OR_LANDLORD`, `ASSOCIATION`, `DMV`, `LIENHOLDER/LESSOR`. One line per recipient: exact requirement in the recipient's words · role **verbatim** (mortgagee, loss payee, additional interest/interested party, additional insured, association certificate holder, lienholder, lessor) · consequence class `NEEDED_TO_CLOSE / NEEDED_BEFORE_KEYS / OPTIONAL` · due date · submission state · acceptance state. Packet line "exact lender name as they want it listed." **Every ledger line accepts owner = household member via §A6 handoff** (shareable script + verification trigger); row menu "someone else is handling this."
**C. Underwriting ledger — carrier only:** inspection/photos/roof/prior-policy history/payment/signed application; each surviving condition is a dated `USER_ACTION_TRACKED`. `CARRIER` is not a proof recipient.
**Master-document object** (condo): one record — `REQUESTED → RECEIVED`, then two independent acceptance states `ACCEPTED_BY_CARRIER` (underwriting ledger references it) and `ACCEPTED_BY_LENDER` (requirement ledger references it). Receipt is one fact, recorded once.
**No recipient (`NONE`)**: "No lender or lease requirement was found. Coverage is your decision — account for it by [responsibility date]." Exits: *Coverage confirmed / I'm deliberately not carrying a policy here / I need to talk to an agent / Come back later (bounded).* Peezy never recommends the choice.

## 8.4 Carrier servicing-channel posture
`CURRENT_SERVICER_IDENTIFIED → GENERAL_CAPABILITY_FOUND → CAN_PLACE_THIS_RISK → COVERAGE_CONFIRMED`, or `CANNOT_PLACE_THIS_RISK`. Primary CTA to whoever services the policy. Leverage line: "Ask your current agent or carrier to re-quote the new address and policy type before you decide whether to stay." Rewrite **never auto-closes** the LEAVING case. ## 8.5 Dates: responsibility anchors, risk-based triggers, external amendment
- New coverage effective: ownership/lease-responsibility begins → move date as labeled planning estimate only. Bind-by: lender's requested proof date → closing coordinator's date → agent's stated lead time → quote expiration → else "Start now," boundary as the protected deadline.
- Old owner end: proposed from sale/possession documents, carrier-confirmed. Old renter end: written release → landlord-confirmed → lease end → key return only when it confirms responsibility ends. Unknown → `DEFERRED` to the event; move date never generates a cancellation.
- **Trigger hierarchy for every WAITING line in this entry (no fixed intervals):** institution-promised date → recipient's required acceptance date → safe bind/effective threshold derived from remaining recovery actions → user-adjustable check date bounded by that threshold → **when the latest safe date has passed: immediate urgent-recovery card, never a backdated reminder.** The former "closing − 14," "~3 business days," and "+3 business days" values are deleted.
- Occupancy mismatch (closing ≠ possession): trigger-only, before any effective-date CTA; owner = carrier/agent.
- **External amendment:** any date/address change after a submission retires stale internal tasks **and** creates an immediate external amend/withdraw action; every milestone with stale evidence reopens.
- Dependency-conflict route (§A4) with explicit exits: carrier issued temporary/conditional proof the recipient accepts · recipient provided a provisional route · still conflicting → carrier escalation / different carrier · support with both named.
- Time-aware CTA.

## 8.7 Retained property and vacancy
Old property kept → role `RETAINED`, lead action "tell your current agent how the property will be used after you move and ask whether the existing policy can remain as written," owner = current agent/carrier, trigger = before move-out / tenant occupancy / carrier deadline. Completes on: coverage confirmed for the new use / replacement or endorsement confirmed / end date confirmed because sold / deliberate no-policy decision with no external requirement. **"I'm handling this outside Peezy" → `USER_ACTION_TRACKED`** (owner = user, action = confirm the post-move disposition, same trigger, resume = retained card) — the same deadlines and warnings, per §A3. **"Someone else is handling it" → §A6 handoff.** `NOT_APPLICABLE` only when the property was generated incorrectly or the household holds no ownership, lease, policy, claim, or financial obligation on it.
Vacancy — trigger-only (move-out before closing · tenant not placed · renovation · second-home absence · utility shutoff · occupancy mismatch · quiet escape) → `CONFIRM_VACANCY_COVERAGE` as `USER_ACTION_TRACKED`; exits *Endorsement confirmed / Current policy covers until [date] / They need a different policy / Couldn't finish.* No period stated. "They won't end it yet" reasons each carry a trigger (sale not closed → WAITING on closing · lender still listed → payoff/mortgagee removal · lease not returned → WAITING on release).

## 9.3 Date model
Per transaction: `LEGAL_TRIGGER · TRIGGER_DATE · PUBLISHED_WINDOW (with source) · LEGAL_DEADLINE · PEEZY_TARGET · DEADLINE_CONFIDENCE`.
- **`TRIGGER_DATE` is derived from the best evidence the rule permits** (wallet document, institution response, system-observed event, explicit user-confirmed event; confidence stored separately) or is `UNRESOLVED`. ## 10.0 Scope and the honest promise
Forwarding is a **backup redirect with a clock**, not an address change. Promise: *get the right USPS request confirmed, know when delivery changes, and keep known senders from being stranded when forwarding ends.* Peezy never enters or stores identity, card, mobile codes, or the USPS confirmation code; only USPS verifies. ## 10.1 Canonical objects and completion

## 10.2 Filing scope — derived; one question only when the roster can't answer
From the roster (people, surnames, who leaves each address, destinations, authority), the responsibility timeline, and known business mail:
- Everyone at the old address moving to the **same** new address **and all movers share the surname and no one with that surname stays** → one **family** request.
- Different surnames, split destinations, or anyone with that surname staying → one **individual** request **per moving person** (there is no "surname group" filing; USPS offers family, individual, or business only). Mail under another name (maiden, prior) → a further individual request via the quiet line "I also get mail under another name."
- Separately moving business → separate business request (link + authority documents; no v1 machinery).
- Already covered by another member's filing → no case.
The one question, only when ambiguous: "Who at [old address] is moving to [new address]?" → *Everyone listed / Edit the people moving.* The filing count renders immediately with the reason once: "USPS verifies each filer — Maya files separately." **Family filing is never proposed while a same-surname resident stays.**
**Ownership:** an adult's individual request is that adult's — prepared fields, one-tap handoff, owner + verification trigger; "someone else is filing" is never terminal. Minors, people unable to act for themselves, a deceased person, or a filer whose ID name differs → the in-person authorized-agent route with its documents (verified), never ordinary self-service.
**Permanent vs temporary:** derived from "will the household return to the old address?" — returning → temporary with start and end (verified min/max rendered from data); not returning → permanent, **even to an interim apartment or a relative's home**. Multiple legs → one filing to the address that should receive mail *now*; when the next address is real, a new `address_leg` filing plus an external amendment to any active earlier request. No pre-built second filing.
**Special routes (trigger-only, official route named, no invented rules):** new address is a PO Box → ordinary route · old address is a commercial mailbox provider → `NOT_APPLICABLE(reason, source)`; the provider owns forwarding; the ledger stays active · international → in-person USPS filing before departure · APO/FPO/DPO → command route first · address USPS won't recognize (new construction) → official address-verification/local Post Office route, then resume · no deliverable destination yet → `DEFERRED` with the ledger still visible.
