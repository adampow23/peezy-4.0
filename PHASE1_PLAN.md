## Scope — five workstreams, each independently shippable, in this order
1. **W1 — Disposition contract field** (additive; client + server). One map field on the task document: `dispositionContract { owner, next_action, next_trigger {kind: date|event, at?, event?, payload?}, resume_destination, visible_status_copy, profile_version }`. Status stays the existing vocabulary; the contract is metadata. Mapper extends (H3), never forks. **[v2] W1 writes the contract field only through the existing status writers — the exhaustive list from the gate: `TaskGenerationService.swift:117,164,248,267`, `TasksStore.swift:80,99,135-137`, `TaskActionService.swift`, `PeezyHomeViewModel`/`FlowEngineView` (orchestrating the shared writers), `spawnTasks.js:259`, `getWorkflowQualifying.js:230,277-287`. Each writer sets `dispositionContract` in the same write it sets `status` (or leaves it absent); no new writer, no separate contract-only write path. `supportAdmin.js` is out of scope (thread status, not task status).** Status copy renders from `visible_status_copy` when present, else existing copy. **No UI beyond copy.**
2. **W2 — Subject-aware canonical keys + H51 fix** (server spawnTasks + client FlowDefinition/FlowEngineView). Spawn request gains `subject { kind: person|pet|vehicle|property|service|child, id }` and `institution` as first-class fields (institution currently only in `titleParams`, H49). Deterministic ID becomes `t2_sha256(householdUid|subject.kind|subject.id|institution|TASK_TYPE)` — a new version prefix, so `t1_` docs coexist and Phase 0's replay path is untouched. Row-expanded `{rowId}.provider` lookup made row-aware in `FlowDefinition`/`FlowEngineView` resolution, with the row-expanded test H51 says is missing.
3. **W3 — Supersession verbs** (server callable + client Change plan). `supersedeTask(taskId, reason, replacement?)` and `reopenTask(taskId, reason)` as one authenticated callable with transactional writes (Phase 0's create-only/transaction discipline); retire marks `Dismissed` with `dispositionContract.supersededBy`. **External amendment** is data only in Phase 1: superseding a task whose contract has `external_submission: true` creates a `USER_ACTION_TRACKED` amend task via spawnTasks (subject-keyed) — the handoff UI is Phase 2.
4. **W4 — Scheduled trigger evaluator** (server; new export type). One `onSchedule` function scanning `dispositionContract.next_trigger` where `kind == date && at <= now` and flipping Snoozed→Upcoming (wake) **[v2] and clearing `snoozedUntil` in the same write, because `TaskRowHeader.swift:11-12,99-105` renders `snoozedUntil` directly and would otherwise show a stale date on a woken row; Phase 2 moves that header to `visible_status_copy`** — or writing `next_trigger.fired = true`; `kind == event` triggers are consumed by a second small path fed from the A11a event envelope written to `users/{uid}/events/{event_id}` (idempotent by `event_id`). No push in Phase 1 (H45 stays; Phase 2). **This is the only new export and the only new subsystem.**
5. **W5 — Rules pass** (firestore.rules). Narrow the recursive owner wildcard so `spawnTokens`, `events`, and `dispositionContract` writes are server-only (H21 consequence), keep direct owner task writes the app relies on (H20 per-actor evidence), **[v2] and validate with `@firebase/rules-unit-testing` against the local Firestore emulator — no such runner exists today (gate item 8: `JoinWaitlistTest.js:193-200` is a source-text assertion only), so W5 adds it as a dev dependency plus one offline suite that encodes H20's per-actor matrix (tasks, assessments, FCM tokens, packing plans, readiness must stay client-writable; inventory, identity, root user, supportChat keep their explicit rules; `spawnTokens`, `events`, `dispositionContract` become server-only). The emulator is local and is not a production-connected test.** No wallet rules yet (Phase 4 per BUILD_BRIDGE).
