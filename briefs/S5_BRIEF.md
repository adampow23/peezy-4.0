## Decisions (owner)

Each of the first three is a contract-legal instrument question, not a taste question: the file the work touches has a frozen owner, so the only lawful shape is a C10.3 ordered-writer row (the S4-CD2/S4-CD5 precedent at L4183/L4185), never a new C10.2 entry, which L4220 forbids because it would install a second writer on another slice's path.

1. **The Home dose keys (carried from the S4 gate, finding 9).** C9.5.16 L2842 is unambiguous: `DailyDoseLocalStore` is the sole process-wide actor and "all `PeezyHomeViewModel` dose reads/writes go through it". Home still uses the three shipped v0 keys through `HomeDoseDefaults`. The obstacle is **not** the test pin, as the S4 ledger recorded: `PeezyNudgeAnswerTests.swift` did move to S5 (L4265/L4196), but the production file does not. `PeezyHomeViewModel.swift` is S4's at unqualified scope (C10.2 L4091) and appears in none of S5's ownership lists, and L4219 bars S5 from writing it merely because a test S5 owns names it. Recommendation: an amendment (S5-CD) adding a C10.3 row in the L4185 shape — "`Peezy 4.0/MainInterface/Models/PeezyHomeViewModel.swift` | S4 owns the file → S5 routes the three dose reads and writes through `DailyDoseLocalStore` under the v2 epoch/revision CAS, and nothing else" — with the file added to S5's exact-scope list and the pinned assertions re-pointed to the v2 state. The alternative the owner may prefer is to leave Home on v0 and register the divergence for S7's pre-ship gate; that keeps a second dose authority alive for one more slice.
2. **The assessment geocode seam (carried from the S4 gate, finding 20).** `AssessmentDataManager.computeDistanceAndInterstate()` applies its result to the shared data manager before any guard can run, so a stale completion's fields survive into a replacement flow. Correcting the S4 ledger's premise: `AssessmentDataManager.swift` **is** an authorized path — S1's, whole scope, at C10.2 L4131, exactly like the frozen `PeezySettingsView.swift` on the line above it — and P1-R's literal closure (L4811) names only `AppRootView.swift`, `PeezyMainContainer.swift` and `AppRootAuthRaceTests.swift`, no assessment file. So the earlier framing ("no other slice owns the file", "P1-R cannot be satisfied without it") was wrong on both halves. Recommendation: an amendment (S5-CD) adding a C10.3 row — "`Peezy 4.0/Assessment/AssessmentModels/AssessmentDataManager.swift` | S1 owns the file → S5 changes `computeDistanceAndInterstate()` to return the computed distance/interstate as an operation-local value, the caller applying it after its UID and load-generation guard, and nothing else" — naming an S1-scope reviewer for the diff. The alternative is to leave the file untouched, keep the guard at the AppRoot and container sites the contract already names, and record the residual stale-completion risk as a ledger line for the owner.
3. **The `inspectCommittedOperation` transports S5's two recovery conformers need.** C9.7.8 requires the `receipt_mismatch` reconcile to run through `inspectCommittedOperation`, the typed callable DTOs live in `TaskPlanService.swift`, and C10.3 L4182 gives S5 "tests only" there. S4 resolved the identical conflict for its own family with S4-CD2. The families S5 needs are three, not two: HANDOFF and HANDOFF_CANCEL for `HandoffSessionStore`, **and WORKFLOW** for `WorkflowService`, whose `DurableStoreRecovering` conformance S5 also writes (L3924) and whose `receipt_mismatch` snapshot carries `store:"workflow"` with `availableActions:["reconcile"]` (L3493, L3540, L3571, L3713). ROUTE_CLAIM stays S7's with `AppRouteInbox`. Recommendation: an amendment (S5-CD) extending the writer sequence to "… → S5 (the HANDOFF, HANDOFF_CANCEL and WORKFLOW `inspectCommittedOperation` transports only)".
4. **Where the real auth-epoch authority lives.** No contract row names `TransitionalFirebaseAuthAuthority`; L4160 authorizes the auth conformances in `AuthViewModel.swift` "with `HandoffSessionStore.swift`", and `TaskPlanDispositionTests.swift` (not S5's) pins `TransitionalFirebaseAuthAuthority.legacyAuthEpochUUID`. Recommendation: the real conformer lands in `HandoffSessionStore.swift` (it owns the durable epoch and the credential revision the C9.7.14 L3935 CAS increments), `AuthViewModel.swift` injects it, and the transitional type stays declared so the S1 pin keeps compiling — a ledger interpretation, no amendment, unless the owner wants the pin retired.
5. **`AppRouteInbox` is S7's.** The handoff store's readiness gates route claim, refresh and returned-session presentation (L3878), but the route store's own `DurableStoreRecovering` conformer is S7's (L3924) and `TaskRouteTests` is S7's new file (L4268). Recommendation: S5 proves the handoff half against a scripted route owner exactly as S4 did, and S7's close-out re-runs the pair and closes P1-P/A3-7 in full — a ledger line, matching L4209's shape for S5.
6. **The handoff store's durable file names.** The contract fixes the route store's names literally (L1922: `PeezyTaskRouteInbox-v1.json`, Application Support, `completeUntilFirstUserAuthentication`; L1923 the quarantine sibling) but names the handoff store only by its `fileKind` (L3463) — a gap, not a convention S5 may fill silently, because recovery fixtures and a second device pin the literal. Recommendation: an amendment (S5-CD) fixing them in the L1922/L1923 shape — `PeezyHandoffAuthority-v1.json` and `PeezyHandoffAuthority-v1.quarantine-v1.json`, Application Support, protection `completeUntilFirstUserAuthentication` — matching the naming pattern S1 and S4 already used for every other durable file.
